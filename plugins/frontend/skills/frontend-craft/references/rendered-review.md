# Review the rendered result

Modified synthesis of Impeccable's separate critique and audit concepts, with the runtime and reporting ceremony removed. See [sources.md](sources.md).

## Gather evidence proportionate to the change

Use the project's existing browser tooling. Open the actual affected route or representative component host. For refinements, inspect the baseline so useful identity and behavior survive. Capture and view the result at a representative wide and narrow width, plus any width or state most likely to expose the changed behavior. A screenshot file that has not been viewed is not visual review.

Inspect the first viewport and the rest of the page; a full-page thumbnail alone can conceal unreadable text or poor controls. Exercise important actions, keyboard focus, and relevant loading/error/empty states. Check content extremes and zoom when layout or typography changed. Record the route, viewport/state, and any material testing limits. Do not claim touch-device testing from a resized desktop viewport.

## Make two distinct judgments

**Design critique:** Before using audit counts as a quality score, assess the brief and the visible composition. What attracts attention first? Is that the right thing? Is the primary action findable? Do typography, spacing, imagery, density, and content form a coherent system? Does a reading page help the reader keep their place? Does an operational interface preserve useful working density? Describe an observed problem and its user effect, not a stylistic dislike.

**Technical verification:** Verify the actual interactions and applicable semantic, keyboard, contrast, overflow, responsive, and public-page checks. Use source inspection and automated tools for evidence they can provide. Passing these checks does not establish good visual design; attractive screenshots do not establish working interactions.

When independent review is available and useful for a substantial change, give the reviewer the brief and rendered artifacts without your self-score. A small correction does not require extra agents or a formal report.

## Correct the highest-impact problem

Prioritize blocked tasks and access failures, then wrong hierarchy or content structure, then consistency and polish. Tie each edit to a specific observation: “the filter summary reads as the page title, obscuring the selected account” is actionable; “make it more premium” is not.

Revisit the affected view after editing, and re-exercise behavior that could regress. Continue while a material issue remains within the authorized scope and a concrete correction is available. Avoid changing a coherent direction merely to make each iteration look different.

Finish when the brief is met, relevant checks pass, and the rendered review finds no unresolved material issue within scope. Summarize what changed and what was verified. If the environment cannot render the page, complete useful source-level checks and identify the missing visual evidence; do not claim visual approval from code alone or silently substitute a different project.
